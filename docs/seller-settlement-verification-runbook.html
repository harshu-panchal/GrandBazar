How to verify all 8 seller settlement rules

A single worked example runs through every section below, so the expected numbers at each step are concrete and checkable — not just "should look about right." Three of these sections cover math that was broken until today (§3 GST refund reversal, §5 restocking fee, §6 partial-return payout proration) — those sections call out old-vs-new numbers explicitly so you can confirm the fix, not just the feature.

Test fixture — set this up once, reuse for every section below

One product, one category, one store config. All expected numbers in this guide are computed from these exact values.

Setup steps

  1. Create/assign the product to a category at /admin/categories/level2. Set Admin Commission = 10%, GST Slab = 12%, and in the Returns & Refunds box, Restock Fee = 20% (leave "Eligible for returns" checked).
  2. On the seller's store (via /admin/sellers/active/:id → Shop Setup, or the seller's own settings), set Packaging Charge = ₹20, enabled.
  3. At /admin/settings, confirm Return Delivery Commission (the flat per-return-pickup fee) is set — use ₹20 for this guide's numbers, or note whatever value is already configured and adjust the expected totals below accordingly.
  4. Place a test order for qty 2 of the product as a customer, same city as the seller (intra-state, so GST splits as CGST+SGST, not IGST).

Known limitation (not a bug, tracked separately): the live commission resolver only checks the subcategory tier — commission set at the Level‑2 category (the one you just configured) or header tier is silently skipped unless nothing more specific applies. For this fixture to show 10% as expected, either set the commission directly on a subcategory, or confirm the product has no subcategory assigned (Level‑2 becomes the deepest applicable tier in that case). If appliedCommissionSourceLevel comes back "shop" or "city" instead of your expected tier, this is why — not a new issue, already on record for a future fix.

05

Settlement considers refund deductions

Fixed 08-15

Two real bugs lived here until today: the restocking fee was configured but never actually applied (dead code — a status field set earlier in the return lifecycle silently bypassed the fee-calculation block every time), and GST was never reversed on refund. Both are fixed — this walkthrough proves it with real numbers.

Steps

  1. Mark the order Delivered (via delivery app or admin override) so a seller Payout gets created — confirm one exists at /admin/wallet with status PENDING, amount ≈ ₹920 (plus delivery/handling if any — packaging is the only piece this guide's fixture adds).
  2. As the customer, request a return for 1 of the 2 units (a partial return — this also sets up §6's prorated-payout check).
  3. As seller/admin, approve the return request.
  4. Move it through pickup → QC → mark QC passed — this is what fires the actual refund (completeReturnAndRefund).

Expected — customer refund (1 unit returned)

StepFormulaValue
Gross item value returned₹500 × 1₹500.00
Restocking fee deducted20% × ₹500− ₹100.00
Net merchandise refund₹500 − ₹100₹400.00
GST refunded12% × ₹400+ ₹48.00
Customer wallet credit₹400 + ₹48₹448.00
Before today's fix, this would have credited a flat ₹500.00 — no restocking fee deducted (the field was dead code) and no GST added back. If you see exactly ₹500.00 credited, the fix isn't deployed/running yet.

Expected — seller clawback (same return)

This walkthrough has the payout still PENDING when the return completes (step 1 above) — that's the "held" case, and it behaves differently from a return on an order whose payout was already released to the seller's available balance. Both are shown below; make sure you're checking the numbers for the scenario you actually set up.

StepFormulaValue
Seller's original payout share for 1 unit₹900 (2-unit line share) × ½₹450.00
If payout still PENDING (this walkthrough)only the merch. share comes off the payout₹450.00
— return-pickup fee in this casenot charged (seller never received the payout yet)₹0.00
If payout already RELEASED (different setup)₹450 debited from available balance + ₹20 return-pickup fee₹470.00

The return-pickup fee only being charged once a payout has actually been released is existing, unchanged platform policy — not something this pass touched. If you want to see the ₹470/released-balance path instead, process the payout (/admin/wallet → process) before starting the return, rather than leaving it pending.

Before today's fix, the seller-side debit used the customer's refund figure instead of what the seller actually received — and if the payout was still on hold, it would have cancelled the entire ₹920 pending payout for a return of just 1 of 2 units, not a prorated ₹450. Check /admin/wallet after this return: if the payout status shows fully CANCELLED rather than reduced to ₹470 remaining (₹920 − ₹450, still HOLD/pending), the proration fix isn't active.

Where to verify

  • • Customer wallet balance (increase of ₹448.00)
  • • Transaction records: one type:"Refund" for the customer (+448), one for the seller (−450 in the pending-payout case, −470 if the payout had already been released) — check meta.gstRefunded / meta.sellerShareOfReturnedItems / meta.returnDeliveryCommissionCharged on each for the itemized breakdown
  • • /admin/wallet: the seller's payout for this order shows reduced to ₹470 remaining (₹920 − ₹450), status still HOLD/pending, not cancelled

07

Settlement considers replacement impact

Verified (pre-dispatch only)

Replacement here means a seller-initiated substitution before dispatch (e.g. an item is out of stock) that the customer approves — not a post-delivery "replace instead of refund" request. That second flow doesn't exist in this app; only the return→refund path (§5) covers delivered orders.

Steps

  1. On a fresh, undispatched order, have the seller propose a replacement item priced within Setting.replacementPriceTolerancePercent of the original (check the configured value at /admin/settings).
  2. Customer approves the replacement.
  3. Repeat with a replacement priced above tolerance, and separately one priced below the original.

Expected

ScenarioExpected system behavior
Cheaper replacementOrder updates to the new item; a real credit-note refund is issued for the difference
Pricier, within toleranceOrder updates; customer is prompted for the extra payment (AWAITING_EXTRA_PAYMENT)
Pricier, outside toleranceRejected — replacement not offered/allowed at that price gap

In every accepted case, re-check paymentBreakdown.sellerPayoutTotal — it should reflect the replacement item's commission/GST/packaging, not the original item's, since it goes through the same recompute-and-freeze path as §6.
