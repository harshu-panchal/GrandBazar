01

Banners, categories, featured products, offers, seller highlights

Wired

Where it lives

Two systems share this ground: Experience Studio (ExperienceSection model) drives banners, curated product rows, and seller-highlight rows; Category Hierarchy is its own CRUD; Offers (Offer / OfferSection) is a parallel system that also powers the separate "Shop by Store" page.

Step by step — banners & curated homepage rows

  1. Log in as admin, open /admin/experience-studio.
  2. Create a new section: pick Page type = Home, Display type = Banners, upload an image, set a link (e.g. link to a category), Status = Active, Save.
  3. Repeat with Display type = Products — pick specific products from the picker instead of a category filter (this is the "featured products" curated row).
  4. Repeat with Display type = Seller highlights — pick 2–3 seller stores.
  5. Drag to reorder the three sections; confirm the order persists after a page refresh.

Step by step — categories

  1. Open /admin/categories/hierarchy.
  2. Create a Header → Category → Subcategory chain; edit commission/handling/packing fields on the category; delete a leaf subcategory and confirm it's removed from the tree view.

Step by step — offers

  1. Open /admin/offers, create an offer (discount %, validity window, applicable category/products), Save, toggle it inactive and confirm it disappears from the public list.
  2. Open /admin/offer-sections, build a curated offer section the same way as an experience section.
  3. Open /admin/shop-by-store — this reuses the same OfferSection backend with sellerIds to build "shop by store" cards. Add a store card here too.

What to verify (customer side)

  • Customer Home page shows the new banner in its carousel, the curated product row with exactly the products you picked, and the seller-highlight row.
  • Offers page shows the active offer and hides the deactivated one.
  • Shop by Store page shows the new store card.
  • New subcategory appears in Categories page and category nav / product filtering.
Known gap: Products also carry a standalone isFeatured checkbox in /admin/products. It saves correctly, but no customer-facing page currently reads that flag to build a "Featured" list — only the curated Experience Studio "Products" row (above) actually surfaces on the storefront. Don't rely on the checkbox alone to make a product show as featured; use the Experience Studio row.
02

Seller recommendations for offline sellers

Wired

The actual feature is "Store Alternatives" — when a store is closed/offline, the customer app suggests open stores in the same category/city. Admin controls which stores are eligible and how many show.

Step by step

  1. Open a seller in /admin/sellers/active/:id → Shop Setup tab → Discovery Controls → check "Exclude from 'Other stores near you' suggestions" → Save.
  2. Open /admin/billing and set the platform-wide alternatives display limit (default 6) to a smaller number, e.g. 2.
  3. As a customer, close a store's operating hours (or ask the seller to toggle themselves offline), then visit that closed store's page.

What to verify

  • The "other stores near you" section on the closed store's page shows open stores in the same category/city, sorted by rating.
  • The store you excluded in step 1 never appears, even if it matches category/city and is open.
  • The list never shows more than the limit you set in step 2.

API reference (public, no auth — useful for a direct check)

GET /api/seller/public/:storeIdOrSlug/alternatives

Response is an array under body.results (plural — this is the array key the whole API uses; the test file's body.result assertion is the bug mentioned above).

03

Configure refunds category-wise

Wired

The backend and the order/return flow fully support per-category refund rules (returnEligible, refundWindowHours, restockFeePercent on Category), and requestReturn genuinely resolves the tightest override across a multi-category order. Fixed 2026‑08‑14: these three fields now have a real admin form — previously API-only.

Step by step

  1. Open /admin/categories/level2 (this is the level that Product.categoryId actually points to — the level the return logic reads).
  2. Add or edit a category → scroll to the Returns & Refunds box at the bottom of the form.
  3. Uncheck Eligible for returns / refund for a non-returnable category (e.g. cosmetics), or leave it checked and set a Refund Window (hours) shorter than the platform default, and/or a Restock Fee (%). Save.
  4. The category list now shows a Returns column — a red "No returns" badge, or the effective window/fee — so this is auditable at a glance without opening each row.

What to verify

  • Place a test order containing only a product from that non-refundable category → the return/refund request is blocked with a message naming that product.
  • Place an order mixing a refundable and a non-refundable category product → the return request still blocks, citing the non-refundable item.
  • Set a category to a shorter window (e.g. 6h) → confirm a return request is rejected once that window elapses, even though the global refundWindowHours in /admin/settings is still 24h.
  • Leave the refund window field blank on a category → confirm it falls back to the platform default rather than blocking returns outright.

Direct API (still available, e.g. for scripted setup)

PUT /api/admin/categories/:id
Authorization: Bearer <admin JWT>
{
  "returnEligible": false,
  "refundWindowHours": 0,
  "restockFeePercent": 15
}
04

Advertisements / Super AD placements

Wired

A dedicated ad-slot type inside Experience Studio — admin picks a seller (and optionally a specific product) per ad slot, sets priority, and the storefront tracks impressions/clicks per slot.

Step by step

  1. Open /admin/experience-studio → Super AD Placements tab.
  2. Add an ad slot: pick a real seller from the dropdown (a fake/unlisted ID is silently rejected — this is intentional validation, see gap-box), optionally a product, upload the ad image, set link type/value and a priority number, Save.
  3. Add a second slot with a higher priority number and confirm it sorts first.

What to verify

  • Ad slot renders on the customer home page in priority order.
  • Clicking the ad navigates per linkType/linkValue (e.g. to the seller's store).
  • Reload the section in admin — impressions/clicks counters on that slot have incremented from your view/click.
Note: placements are not tied to seller billing/subscription in code — any admin can assign any seller to a slot for free. If "Super AD" is meant to be a paid product, that's a product decision still to be designed, not a bug.
05

Dynamic sections & platform rules

Wired

"Dynamic sections" = the same Experience Studio system as §1/§4 (reorderable, typed homepage blocks). "Platform rules" = the global Setting singleton — pricing mode, surcharges, refund window, operating hours, bulk-order thresholds, product-approval toggles, etc.

Step by step — platform rules

  1. Open /admin/settings. Change Operating Hours cutoff, toggle odd-hour surcharge on with an amount, Save.
  2. Open /admin/billing for commission/bulk-order threshold fields (bulkOrderQtyThreshold, bulkOrderValueThreshold, bulkOrderCommissionRate) and the alternativesDisplayLimit field from §2. Change one, Save.
  3. Reload each page fresh (hard refresh) — confirm the values you set are still there, not reverted to defaults. This is the exact class of bug fixed in prior remediation (settings silently not persisting) — worth re-checking on every field you touch here.

What to verify

  • Checkout math reflects the odd-hour surcharge / operating-hours cutoff you set.
  • An order over the bulk-order value/qty threshold gets flagged/commissioned per the bulk-order rate.
  • Dynamic-section reordering from §1 persists after refresh.
06

Seller shop setup on behalf of seller

Wired

Step by step — create a seller + shop from scratch

  1. Open /admin/sellers/pending → Create Vendor Account. Fill seller + shop details, submit.
  2. Confirm the seller receives welcome-email credentials (check the configured mail sink / logs in dev), and the store appears in /admin/sellers/active immediately, without the seller having done anything.

Step by step — edit an existing seller's shop

  1. Open /admin/sellers/active/:id → Shop Setup tab.
  2. Edit shop name, description, address/locality/city/pincode, service radius, packaging charge, banners/video, bank details (account/IFSC/PAN/GST), and the open/verified toggles. Save.
  3. Use Resend credentials and confirm a new email goes out.

What to verify

  • Changes reflect immediately on the seller's public store page and in the seller's own dashboard (log in as that seller to confirm they see the admin-made edits, not stale cached data).
  • Bank/PAN/GST fields round-trip correctly (re-open the tab after Save, values are still there).
07

Seller settlement & bulk-order settlement

Wired

Step by step — general settlement

  1. Open /admin/wallet. Filter by seller payouts, pending status.
  2. Pick a pending payout → hold it with a reason, confirm status flips to HOLD; release it, confirm it returns to PENDING.
  3. Apply a manual adjustment (e.g. −₹50 for a packing complaint) to a payout, confirm the amount and the adjustment note both update.
  4. Process a batch of payouts, then export the statement CSV and spot-check totals.

Step by step — bulk-order settlement

  1. On the same /admin/wallet page, tick the "Bulk orders only" filter checkbox.
  2. Confirm only payouts with isBulkSettlement: true remain in the list — these are payouts generated from orders that crossed the bulk-order qty/value threshold set in §5. Each carries a purple BULK badge next to the seller name.
  3. Fixed 2026‑08‑14: click the new Breakdown button on a bulk payout row → a modal shows the actual per-order split (seller payout / commission / packaging / tax) plus settlement status, pulled straight from the BulkSettlement record for that order.

What to verify

  • The four breakdown figures (seller payout, commission, packaging, tax) sum to the order's expected total — spot-check against the order detail page.
  • Breakdown status shows PENDING for an unprocessed payout, then flips to COMPLETED with a settled-on date after you process that payout.

API reference

GET /api/admin/finance/bulk-settlements?orderId=...&status=...&sellerId=...

New endpoint, admin-only. Paginated, same envelope shape as /finance/payouts.
